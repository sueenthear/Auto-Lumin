# audio_manager 功能交接（已完成）

> 状态：**功能实现完成并通过单测与真实进程隔离验证**。当前工作位于本地分支 `feature/do-audio`，没有提交或推送。包内已包含用户录制的真实模板 `script_core/audio_manager/template.voice`（由 `template_cut1.wav` 就地改名，音频内容未改动）。

## 目标与已确认决定

- `do.audio.listen.start(template=None)`：仅监听当前 `Core(...)` 绑定窗口所属进程及其子进程的播放音频；传入 `.voice` 路径，未传入时**只查包内** `template.voice`（工作目录同名文件被忽略）。
- `do.audio.listen.threshold(value)`：设置匹配阈值，要求 `(0, 1]`，默认 `0.8`。
- `do.audio.listen.stop()`：停止监听；`do.audio.action(func)`：注册匹配后调用的无参数函数。`do.audio.listen.listening` / `error` 可查询状态。
- 只支持能够使用 Windows 进程专属 loopback 的 **Build 20348+**；不支持时明确报错，**不回退为系统混音**，否则无法保证只采集目标 exe。
- `.voice` 的内容采用标准 RIFF/WAV：16 kHz、单声道、signed PCM16，可由普通支持 WAV 的播放器读取；保留 `.voice` 扩展名。
- 音效匹配越过阈值触发一次；约 40 毫秒静音或一个模板长度的持续不匹配后重新武装，因此连续播放会再次触发。

## 本轮修复的关键问题

1. **COM 回调生命周期**：`ActivateAudioInterfaceAsync` 的完成回调先 `SetEvent` 再返回，若此时释放回调对象或 `operation`，Windows 仍可能调用已释放的 vtable 导致崩溃。现在回调对象与激活参数在进程内保持存活，超时后由回调线程自行释放 `operation` 与 `IAudioClient`。
2. **STA 线程兼容**：`CoInitializeEx` 返回 `RPC_E_CHANGED_MODE` 时不再报错（GUI 主线程已处于 STA），且不误调用 `CoUninitialize`。
3. **启动失败清理**：`start()` 在激活失败、无权限或超时后抛出异常并回收监听线程，`error` 保留原始原因；窗口失效在打开采集前即拒绝。
4. **重复触发**：一次 `read()` 可能包含多个音频包，管理线程按 50 毫秒分块送入匹配器；重新武装改为“静音 40 毫秒或持续不匹配一个模板长度”，避免同一段声音被切成两次触发。
5. **录音校验**：时长参数拒绝布尔、`nan`、`inf` 与非数值；空录音不会覆盖目标文件；`.voice` 帧数据不完整时报错而不是静默截断。

## 尚未验证 / 已知限制

1. 未在真实游戏进程上长时间运行；游戏内实际音效与模板的相似度阈值仍需按现场调优。
2. 包内模板只有 0.263 秒、峰值 810，素材偏短偏轻；若实际触发不稳，建议用录音工具重新录制更长的提示音片段覆盖 `script_core/audio_manager/template.voice`。
3. 动作回调在独立线程执行，未注册动作或上一动作仍在运行时不会重入；动作抛出的异常会写入 `error` 并停止监听。
4. 模板查找已改为**只查包内**；工作目录或 `example/` 下的 `template.voice` 不再参与匹配，避免脚本目录的遗留文件悄悄改变行为。需要临时换音效时显式传路径。
5. 是否分发游戏音频素材需用户确认。
